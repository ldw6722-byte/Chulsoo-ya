# 판매자 온보딩·검증 계약

## 구현 범위

관리자 매장 직접 등록 CRUD는 유지한다. 로그인한 일반 사용자가 사업자 정보를 제출하고, 관리자가 증빙을 검토해 **승인 시에만** 판매자 역할과 매칭 가능한 매장을 생성하는 별도 흐름을 추가한다.

| 단계 | 행위자 | REST API | 서버 확정 결과 |
| :--- | :--- | :--- | :--- |
| 신청 | `CONSUMER` | `POST /api/seller-applications` | 신청 레코드 생성, 상태 `PENDING` |
| 내 신청 조회 | 신청자 | `GET /api/seller-applications/me` | 본인 신청과 검토 상태만 조회 |
| 증빙 업로드 | 신청자 | `POST /api/seller-applications/{id}/business-license` | 허용 파일만 비공개 Storage에 UUID 객체 키로 저장하고 메타데이터 갱신 |
| 심사 목록 | `ADMIN` | `GET /api/admin/seller-applications?status=` | 신청자·상태·제출 시각 기준 목록 조회 |
| 승인 | `ADMIN` | `POST /api/admin/seller-applications/{id}/approve` | 신청자를 `SELLER`로 변경하고 미검증 매장 1개를 생성 |
| 반려 | `ADMIN` | `POST /api/admin/seller-applications/{id}/reject` | 반려 사유와 검토자·시각을 불변 기록 |

## 비파괴 마이그레이션 V7

```sql
create table seller_applications (
    id bigint generated by default as identity primary key,
    applicant_user_id bigint not null unique references users(id),
    store_name varchar(100) not null,
    representative_name varchar(100) not null,
    business_registration_number varchar(20) not null,
    business_opened_on date,
    city_name varchar(60) not null,
    district_name varchar(60) not null,
    gu_code varchar(20) not null,
    address varchar(300) not null,
    phone varchar(255) not null,
    handled_items varchar(1000),
    status varchar(20) not null default 'PENDING',
    nts_status varchar(30) not null default 'NOT_REQUESTED',
    nts_message varchar(500),
    certificate_object_key varchar(500),
    certificate_content_type varchar(100),
    certificate_size_bytes bigint,
    submitted_at timestamptz not null default now(),
    reviewed_by bigint references users(id),
    reviewed_at timestamptz,
    rejection_reason varchar(500),
    version bigint,
    constraint ck_seller_application_status check (status in ('PENDING', 'MANUAL_REVIEW', 'APPROVED', 'REJECTED')),
    constraint ck_seller_application_nts_status check (nts_status in ('NOT_REQUESTED', 'VERIFIED', 'MISMATCH', 'UNAVAILABLE')),
    constraint ck_seller_application_certificate_size check (certificate_size_bytes is null or certificate_size_bytes between 102400 and 5242880)
);
create index ix_seller_applications_status_submitted on seller_applications(status, submitted_at);
```

`business_registration_number`는 심사용 제한 데이터이며 공개 API 응답에 포함하지 않는다. 파일 원본명은 DB에 저장하지 않고, 응답에 제공하지 않는다. 공개 URL을 생성하지 않으며, 관리자와 신청자만 서버가 발급한 단기 접근 URL을 조회할 수 있다.

## 파일 검증

| 항목 | 규칙 |
| :--- | :--- |
| 허용 형식 | `image/jpeg`, `image/png`, `application/pdf` |
| 용량 | 100KB 이상, 5MB 이하 |
| 객체 키 | `seller-applications/{applicationId}/{uuid}` |
| 버킷 | Supabase Storage 비공개 버킷 `seller-verification-documents` |
| 금지 | 클라이언트 파일명·확장자 신뢰, 공개 버킷, 서비스 키의 프론트엔드 노출 |

## 상태 전이와 권한

```text
PENDING 또는 MANUAL_REVIEW
  ├─ 관리자 승인 → APPROVED + users.role=SELLER + stores.verified=false
  └─ 관리자 반려 → REJECTED
```

매칭 엔진은 기존 `stores.verified=true`만 허용하므로, 승인된 매장은 관리자 검토 후 운영 가능 상태로 전환한다. 이 분리는 사업자 승인과 매장 운영 활성화를 혼동하지 않기 위한 것이다. 동일 사용자는 `seller_applications.applicant_user_id` 유니크 제약으로 신청을 하나만 갖는다.

## TDD 계약

1. 일반 사용자는 유효한 신청을 제출할 수 있고, 다른 사용자의 신청은 조회·수정할 수 없다.
2. 이미 신청한 사용자는 중복 신청할 수 없다.
3. 100KB 미만, 5MB 초과, JPEG/PNG/PDF 외 형식은 증빙 업로드 전에 거부한다.
4. 관리자가 신청을 승인하면 역할은 `SELLER`가 되고, 해당 소유자 매장이 정확히 하나 생성된다.
5. 중복 승인 요청은 두 번째 매장 또는 역할 변경 부작용을 만들지 않는다.
6. 반려는 사유 없이 처리할 수 없으며, 반려 후에는 승인 처리할 수 없다.
7. 신청자와 관리자가 아닌 요청자는 신청 목록·증빙에 접근할 수 없다.

## 외부 연동 경계

국세청(NTS) 실연동과 Supabase Storage 버킷 생성은 공급자 키·버킷 정책이 준비된 뒤 어댑터에서 활성화한다. 이 값들은 환경변수에만 두고 코드·마이그레이션·프론트엔드에는 기록하지 않는다.
